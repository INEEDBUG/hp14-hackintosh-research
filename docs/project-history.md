# 项目经历与决策

这是一项仍在进行的单机兼容性研发，目标是让既有 HP14 在保留稳定显示与启动成果的条件下，逐层验证原生无线、睡眠和连续互通。以下为既有记录的脱敏整理，不是逐分钟原始日志，也不补造每次实验的准确日期。

## 已完成的基线与验收

1. 建立可恢复的启动环境，保留稳定内屏、正常物理光标、触控板与启动表现。已知稳定图形基线包含 `8A520000`、51 MiB stolen memory，以及既有 WhateverGreen / ACPI 配置。
2. 把实验放在隔离工作区与测试 USB，避免覆盖稳定内部 EFI；每个现场批次保存回退材料。
3. 从 itlwm + HeliPort 迁移到系统原生 Wi-Fi 界面候选。用户验收扫描、连接、开关重连与桌面输入；随后发现稳定性问题，因此将状态从基础烟测通过调整为“日用稳定性未验收”。
4. 用户完成独立身份候选下的 Apple ID 与 FaceTime 登录。账号、验证码及机器身份从未作为公开材料。

## 睡眠研发的有效收敛

macOS 的系统与远程访问可以从睡眠恢复，但物理内屏仍黑。`dc6config=0` 实际加载后故障仍出现，排除了“加上这个参数就完成修复”的假设。

GitHub / Reddit / 专业社区的相似 Ice Lake 案例提供了平台表线索。对本机系统版本做离线表字段比较后，仍未建立能够修正当前面板故障的可验证机制，因此没有把相似机型参数直接合入日用环境。

临时 Linux 在同一台机器、同一面板和无电池条件下完成了一次深度睡眠唤醒，用户确认内屏及命令行恢复。这使排查进一步聚焦 macOS 驱动、面板初始化和恢复路径，但没有单凭对照宣判某个驱动函数为根因。

面板时序候选的 macOS 现场测试仍黑屏。后续诊断驱动部分批次在启动采集阶段未满足观测门槛，均回退；这些批次不能算睡眠修复验证。最新离线方向围绕固定内屏的 HPD / AUX 判定，实机有效性仍未建立。

## AirDrop 研发的有效收敛

Finder 中能发现自己的 iPhone，但文件发送持续等待，反向传输未通过。把“发现设备”“原生 Wi-Fi 可用”“AirPlay 可显示”与“AWDL 链路及双向文件传输”分别记录。

研究了 itlwm 分支、OWL、OpenDrop 及相关 Linux / Windows 工程。OWL 的既有离线测试曾完成 52 项；这不说明 HP14 的 macOS 驱动具备 monitor / injection 能力，也不说明 Finder 原生 AirDrop 已接通。当前不以第三方用户态界面替代原生双向 AirDrop 的验收。

## 2026-10-13：Wi-Fi 稳定性离线里程碑

用户报告三个问题：跨路由器切换失败、扫描慢、自动断开后重连。先保存当前实际驱动和系统版本，检查对应源码与上游扫描游标 PR。

对实际生产函数建立主机边界测试，复现 5 个失败；实现扫描游标重置、节点生命周期修正、门内串行化和速率数组边界修正。当前 14 项测试全部通过，完整实验驱动编译链接成功。新增数值诊断用于下一次现场验证实际扫描路径、关联拒绝与首次掉线事件。

这是一项源码和离线验证进展。实机网络切换速度、稳定性和固件行为尚未验证；睡眠与 AirDrop 也仍然 OPEN。

## 公开同步约定

每个实质性里程碑提交对应问题、变化、验证和限制；现场失败记录真实结果。新源码与工具先检查许可证、再脱敏并验证复现路径。后续睡眠及协议研究中适合复用的代码会在对应审查通过后追加，私人原始证据留在本地。
